# Такт — насыщение линии 1 составами

Прототип для вектора 2 кейса «Петербургский метрополитен» (Сириус, 2026). Каждые 15 минут Такт сравнивает фактический вход пассажиров с тем, на что рассчитан график, прогнозирует поток на 15–120 минут, считает загрузку состава на критических перегонах и рекомендует, что делать с составами, проверяя ограничения линии.

## ТЗ → как сделано → где смотреть

| Шаг ТЗ (вектор 2) | Как сделано | Где смотреть |
|---|---|---|
| 1. Сбор: турникеты по 15 минут, тип дня, внешние факторы | входы 24 вестибюлей, сведённые к 19 станциям; тип дня и праздники; событий в данных нет; погода — Open-Meteo, только для показа | `pipeline/data.py` |
| 2. Прогноз на 15–120 мин по станциям, сравнение с базовым, типичный или аномальный день | «обычный день» по прошлым неделям × поправка на последний час; проверка на июле и сентябре; метка дня на пульте и календарь аномалий | `pipeline/forecast.py`, сайт: «Пульт», «Дни» |
| 3. Оценка достаточности: загрузка в норме или выше порога | загрузка состава на критических перегонах против нормы 960 (120 чел. × 8 вагонов); загрузку платформ по входам без выходов не оценить | `pipeline/engine.py`, «Пульт» |

| 5. Оценка эффекта | 120 дней проигрываются с мерами и без; поездо-часы и время ожидания в рублях с источниками | `pipeline/simulate.py`, `pipeline/economics.py` |

| Сверх ТЗ | по тем же данным видно, что лист графика сам снимает составы в 09:00 при перегрузке; предложение и варианты с ценой | сайт, «График» |

## Кто пользуется

- **Поездной диспетчер** — каждые 15 минут, «Пульт». Это то, что просит ТЗ: график остаётся, Такт подсказывает корректировку в конкретный момент и проверяет её по ограничениям линии.
- **Служба, которая составляет лист графика** — раз в сезон, «График». Это находка сверх ТЗ: утренняя перегрузка с севера повторяется каждый будний день, поэтому её дешевле убрать в самом листе графика, чем каждое утро решать на пульте.
- **Все** — «Дни»: календарь, где поток шёл не так, как обычно.
- **Старший диспетчер, аналитик** — «Разбор»: все советы дня и что с ними решил диспетчер. Журнал хранится только в браузере, на сервер ничего не уходит.

На «Пульте»: полоса состояния, одно решение движка (через сколько станет тесно, до скольки человек, что делать); карточка совета с кнопками «Принять» (с подтверждением смен машинистов и отменой), «Напомнить через 15 мин», «Не нужно» (с причиной); коридор загрузки на 2 часа и схема линии. Принятое и отклонённое сразу меняет расчёт дня: отказ не возвращается тем же советом, принятое меняет интервал и прогноз загрузки. Режим «Показ» считает прошлые советы принятыми, «Рабочий» только принятые. Загрузка составов по входам считается только утром (до 11:00): вечером нужны выходы, их нет, и Такт честно пишет, что не оценивает. Основание — `docs/research/ideal-solution-analysis.md` и `docs/research/ux-analogs-and-ideas.md`.

## Как запустить

Все данные уже в репозитории, сайт запускается сразу:

```bash
cd site && npm ci && npm run dev
```

Пересчитать всё с нуля из исходного архива ментора (`data/raw`):

```bash
python3 pipeline/load_raw.py data/raw   # таблицы входов data/*.csv.gz
python3 pipeline/export.py              # расчёт и выгрузка для сайта в site/public/data (≈1 мин)
```

Нужны Python 3.11+, numpy, pandas, lightgbm, openpyxl; Node 20.

## Устройство

- `pipeline/line.py` — станции, листы графика, ограничения линии; у каждой величины указан источник.
- `pipeline/baseline.py` — «обычный день» строго по прошлым дням.
- `pipeline/forecast.py` — модели прогноза и проверка во времени (февраль и май → июль и сентябрь).
- `pipeline/engine.py` — загрузка на критических перегонах и решение с проверками 1:53, 53 состава, резерв.
- `pipeline/simulate.py` — проигрывание всех 120 дней с 15-минутными данными.
- `pipeline/anomalies.py`, `pipeline/economics.py` — аномальные дни и финансы с источниками.
- `site/` — Vite + d3, только рисует `site/public/data/*.json`.

## Проверки

`python3 -m pytest tests`: ограничения линии на всех 120 днях (интервал 1:53, 53 состава, выход резерва не раньше чем через 20 мин, снятие только днём), отсутствие подглядывания в будущее у прогноза и базы, согласованность цен и источников, оценка α и **совпадение расчёта на сайте (`site/src/lib/engine.js`) с Python на 7 680 решениях** (`tests/parity.mjs`). Проверки ловят порчу констант и логики: порча α, лимита составов, времени выхода резерва, границы утреннего окна и часов снятия валит тесты. GitHub Actions (`.github/workflows/check.yml`) ставит `requirements.txt`, запускает тесты, **пересчитывает выгрузку и требует, чтобы она совпала с лежащей в репозитории**, и собирает сайт.

Что лежит в репозитории: `data/raw` — архив ментора как есть, `data/*.csv.gz` — входы по вестибюлям из него, `site/public/data` — готовая выгрузка для сайта.

## Ограничения

- Выходов по станциям нет: вечернее направление из центра и загрузку на пересадочных станциях по турникетам не оценить. Загрузка по входам считается только утром, до 11:00.
- Доля α не измерена. При 0,75 перегрузок вдвое меньше и меры почти ничего не дают по давке (−2%); при 0,85 −16%. Время ожидания от α не зависит.
- Загрузка посчитана той же формулой, что и прогноз, и не сверена с датчиками РПДП (они есть только снимками одного состава). Максимум в данных 1 337 человек на состав, выше предела 1 458 не бывает.
- Исполненного графика нет, лист задан по часам: гипотеза «09:00 → 09:30» требует проверки по исполненному графику.
- Смены машинистов и окна осмотра в депо в данных нет: на пульте совет, добавляющий машинисто-часы, подтверждается только отметкой «смены проверил».
- Резерв: горячий 2+2 выходит за 15–20 мин, холодные составы за 30. В слотах по 15 минут первый слот выпуска для тех и других через 30 мин, поэтому предел даёт линия (53 состава, 1:53). Сколько холодных составов в депо, неизвестно.
- Для февраля и мая взят лист «рабочий с 01.09»: зимнего листа нет.
- Прогноз почти не лучше «обычного дня» на уровне станций и в пиковом окне; его польза в меньшем числе ложных тревог, а главная ценность Такта — совет с проверкой ограничений в конкретный момент.

Сайт — рабочие экраны для людей; расчёты, деньги и источники — в `pipeline/` и в этом README.
