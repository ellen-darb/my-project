# Бизнес-обоснование: «Советник диспетчера» для Линии 1

Все цифры ниже посчитаны на данных, которые передал ментор, или выведены из них формулой. Чего в данных нет, помечено как «подставит метрополитен».

## 1. Проблема и её стоимость

Плановый график Линии 1 задаёт парность по часам и типу дня. В пик по графику на линии около 50 составов (29–30 пар в час при максимуме 31,9). Это почти потолок: интервал не меньше 1:53, оборот линии 99 минут, на линии не больше 53 составов. Запаса по добавлению составов в пик немного, поэтому решение «добавить состав» нужно принимать заранее, а не когда платформа уже полна.

Обратная сторона: в часы с низким потоком график выпускает больше составов, чем нужно. По модели загрузки вагон в такие слоты заполнен меньше чем на 40% нормы 120 чел/вагон.

Как решается сегодня: диспетчер смотрит на ситуацию и звонки со станций. Прогноза на 30–120 минут у него нет, а резерв выходит на линию 15–20 минут.

## 2. Пользователи и сценарии

- Поездной диспетчер: получает подсказку «добавить N составов к ЧЧ:ММ из депо X» или «снять N составов», видит причину и ожидаемую загрузку. Решает сам.
- Аппарат главного диспетчера: видит день целиком (норма, факт, прогноз) и оценку, какие станции дают поток на перегруженный перегон.
- Служба эксплуатации: смотрит итоги за период (сколько перегрузов предотвращено, сколько поездо-часов сэкономлено).

## 3. Альтернативы

| Подход | Результат на истории (83 будних дня, 11 интервалов с перегрузом по модели) |
|---|---|
| Текущий процесс: опыт диспетчера и звонки | прогноза нет, реакция после роста потока |
| Решение по последнему наблюдённому слоту | видит 0 из 11 перегрузов: поток растёт быстрее, чем успевает выйти резерв |
| Норма дня для слота без ML | видит 11 из 11, но даёт 232 сигнала |
| Наш подход: норма дня + ML-поправка по свежему отклонению | видит 11 из 11 при 164 сигналах |

ML не находит больше перегрузов, чем норма дня. Он убирает около 30% лишних сигналов при том же охвате и точнее прогнозирует поток (ошибка на 30 минут 4,4% против 7,7% по линии и 9,6% против 12,5% по станциям).

## 4. Эффект и экономика

Источник: бэктест на 83 будних днях (февраль, май, июль, сентябрь 2026). Прогноз каждого месяца делает модель, которая этот месяц не видела, база нормы дня берётся по другим месяцам, профиль распределения поездок тоже по другим месяцам.

| Показатель | Значение |
|---|---|
| Интервалов 15 мин с загрузкой выше 120 чел/вагон | 11 по графику, 7 с рекомендациями |
| Пассажиров сверх нормы вагона | −56% |
| Перегрузов, замеченных за 30 минут | 11 из 11 при пороге сигнала 85% нормы |
| Сигналов «добавить» | 164 за 83 дня (около 2 в день), верных 11, точность 7% |
| Цена всех сигналов «добавить» | 59 поездо-часов за 83 дня, около 0,7 в сутки |
| Потенциал снятия составов в недогруженные слоты | 27 поездо-часов в сутки, 4,3% плана (643 поездо-часа в сутки по графику оборота) |
| После снятия составов вагон выше 95% нормы | 0 случаев |

**Порог сигнала.** Порог подобран по таблице на тех же данных (`pipeline/thresholds.json`), поэтому это настройка, а не независимая проверка:

| Порог | Сигналов ML | Перегрузов замечено ML | Сигналов нормы дня | Перегрузов замечено нормой дня |
|---|---|---|---|---|
| 80% | 270 | 11 из 11 | 290 | 11 из 11 |
| 85% | 164 | 11 из 11 | 232 | 11 из 11 |
| 90% | 92 | 7 из 11 | 150 | 10 из 11 |
| 95% | 56 | 1 из 11 | 23 | 0 из 11 |
| 100% | 16 | 0 из 11 | 0 | 0 из 11 |

**Что система не снимает.** Рекомендация упирается в интервал 1:53 и 4 резервных состава: один–три добавленных состава снижают загрузку на 2–4% нормы, поэтому перегруз не исчезает полностью (11 → 7). Когда лимит исчерпан, система называет станции для ограничения входа. Сигнал при 85–100% нормы в интерфейсе подписан как «Подготовить резерв».

**Формула экономии:** `Э = 27,4 поездо-ч × 250 рабочих дней × C`, где C — полная стоимость поездо-часа (энергия, износ, ресурс по пробегу). Стоимости поездо-часа в данных нет, её подставит метрополитен. Каждые 1000 ₽ за поездо-час дают около 6,8 млн ₽ в год на одной линии. Это потенциал: расчёт идёт по 15-минутным слотам, а состав с оборотом 99 минут снимается не на слот, поэтому реальную экономию нужно пересчитать по графику оборота.

**Чувствительность к калибровке.** Загрузка вагона оценена моделью, поэтому абсолютное число перегрузов зависит от допущений: как далеко едут пассажиры (λ) и масштаб потока (`pipeline/sensitivity.py`):

| Допущение | Перегрузов по графику | С рекомендациями | Замечено за 30 мин (по последнему слоту) | Потенциал снятия, поездо-ч за 83 дня |
|---|---|---|---|---|
| базовое (λ=6, масштаб 1,0) | 11 | 7 | 11 из 11 (0) | 2272 |
| дальние поездки (λ=12) | 132 | 47 | 127 из 132 (18) | 518 |
| поток +10% | 121 | 56 | 115 из 121 (21) | 904 |
| поток −10% | 0 | 0 | перегрузов нет | 3664 |
| короткие поездки (λ=3) | 0 | 0 | перегрузов нет | 6150 |

Где перегрузы есть, прогноз замечает 95–100% из них, последний слот не больше 17%, рекомендации убирают 36–64% перегрузов. Потенциал снятия составов при этом идёт в обратную сторону от перегрузов (от 518 до 6150 поездо-ч), то есть оба эффекта сразу высокими не бывают. Это снимается калибровкой по весовым датчикам или по числу реальных случаев выше 120 чел/вагон, которое назовёт метрополитен.

**Честные оговорки.**
- На обычных днях перегрузов мало (11 интервалов из 5810 по базовой модели). Ценность по перегрузу проявится на аномальных днях (погода, матч, сбой наземного транспорта), но погоды и мероприятий в данных нет.
- На демо-дне 08.05 (пятница перед праздниками) поток после обеда на треть выше нормы, а по дню целиком +5%. База «пятница» общая для обычных и предпраздничных дней.
- Загрузка вагона оценена моделью по входам турникетов. Данные весовых датчиков не использованы.
- Оценка сделана на горизонте 30 минут. На 60 и 120 минут измерена только ошибка прогноза потока (5,3% и 6,2% по линии), решения не оценивались.

## 5. Стоимость владения

- Вычисления: обучение модели занимает несколько минут на одном процессоре, расчёт рекомендации занимает миллисекунды. Внешних платных API нет.
- Данные: те же 15-минутные выгрузки турникетов, которые метрополитен уже ведёт.
- Поддержка: переобучение раз в месяц по расписанию, контроль точности прогноза (ошибка на 30 минут сейчас 4,4% по линии).
- Интеграция: для пилота достаточно выгрузки турникетов и графика. Подключение к системам диспетчерской нужно только на этапе промышленной эксплуатации.

Сумму в рублях метрополитен считает по своим тарифам: в данных нет ни стоимости разработки, ни стоимости эксплуатации серверов.

## 6. Внедрение

1. Пилот в теневом режиме, 4 недели: система выдаёт рекомендации, диспетчер их не видит. Сравниваем с реальными решениями диспетчера.
2. Показ диспетчеру, 4 недели: рекомендации на экране, решение остаётся за ним. Метрики успеха: доля принятых рекомендаций, число интервалов выше нормы, сэкономленные поездо-часы.
3. Подключение погоды и календаря мероприятий.
4. Масштаб на другие линии.

## 7. Риски и ограничения

| Риск | Мера |
|---|---|
| Модель загрузки вагонов оценочная | Калибровка по датчикам РПДП на пилоте; до калибровки рекомендации идут с запасом (сигнал при 90% нормы) |
| Нет погоды и событий в обучении | Подключить как признаки на пилоте, пока работает календарь и свежее отклонение потока |
| Ошибочный сигнал | Решение остаётся за диспетчером; все сигналы «добавить» вместе стоят около 0,7 поездо-часа в сутки, но их около 2 в день при точности 7%: порог подбирается на пилоте по доле принятых сигналов |
| Предел линии (1:53) | Система показывает, когда добавлять составы нельзя, и называет станции для ограничения входа |
| Плановая парность выходных не передана | Оценка по выходным не делалась, добавится после передачи графика |

## 8. Масштаб и развитие

Те же входные данные (турникеты по 15 минут и график) есть по другим линиям. Логика переносится заменой справочника ограничений линии (оборот, число составов, резерв). Число других линий и стоимость внедрения на них в данных ментора не указаны.
